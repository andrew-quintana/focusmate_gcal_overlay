# RFC 001 — Focusmate Calendar Overlay Chrome Extension (Technical Design)

## Design Overview

This RFC defines the technical architecture for a Chrome Extension (Manifest V3) that overlays Google Calendar events on the Focusmate web app and highlights scheduling conflicts. The entire codebase will be implemented in TypeScript for type safety and maintainability.

### High-Level Architecture

The extension consists of four main components:
1. **Background Service Worker** (`background.ts`) - Handles OAuth, API calls, and conflict computation
2. **Content Script** (`content.ts`) - Renders overlay UI and applies conflict styling to Focusmate DOM
3. **Options Page** (`options.ts` + `options.html`) - User configuration interface
4. **Shared Types & Utilities** (`types/`, `utils/`) - Type definitions and pure functions

### Key Design Decisions

1. **TypeScript-First**: All source code in TypeScript, compiled to JavaScript for Chrome runtime
2. **Shadow DOM**: Overlay uses Shadow DOM for style isolation
3. **Message Passing**: Content script communicates with background via `chrome.runtime.sendMessage`
4. **Caching Strategy**: 60-second cache for Google Calendar API responses
5. **DOM Resilience**: Multiple selector strategies for Focusmate session detection

### Phase 2: Background Service Worker

**Core Responsibilities**
1. Google OAuth token management via `chrome.identity` (support multiple accounts)
2. Google Calendar API integration (primary source of truth for sessions when sync enabled)
3. Focusmate API integration (optional fallback; not reliable for date ranges)
4. Conflict computation
5. Message handling from content script

- In-memory cache keyed by `calendarIds + timeMin + timeMax`
- 60-second TTL
- Clear cache on settings change

**Shadow DOM Implementation**
- Create isolated Shadow DOM for overlay
- Inject styles into shadow root
- Use `:host` selector for container styling
- Prevent style leakage to Focusmate page

**MutationObserver Strategy**
- Observe calendar grid container
- Debounce callbacks to 200ms
- Reapply conflict styling on mutations
- Handle route changes by detecting DOM replacement

## Technical Decisions

### Decision 1: TypeScript Compilation Target
**Choice**: ES2020 with module system compatible with Chrome extensions
**Rationale**: Modern JavaScript features while maintaining Chrome compatibility

### Decision 2: Build Tool
**Choice**: Webpack or Rollup (to be determined)
**Rationale**: Standard tooling for TypeScript bundling, supports code splitting if needed

### Decision 3: Shadow DOM for Overlay
**Choice**: Use Shadow DOM for style isolation
**Rationale**: Prevents CSS conflicts with Focusmate page, maintains encapsulation

### Decision 4: Caching Strategy
**Choice**: 60-second in-memory cache for Google Calendar API responses
**Rationale**: Reduces API calls, improves performance, stays within rate limits

### Decision 5: Google Calendar as Primary Source of Truth
**Choice**: Prefer Google Calendar API for session data, especially when Focusmate→Google Calendar sync is enabled
**Rationale**: Google Calendar provides reliable date range querying. When sync is enabled, Focusmate sessions appear as Google Calendar events, eliminating need for Focusmate API. Focusmate API is optional fallback only.

### Decision 6: Derived Keys for Session Identification
**Choice**: Use derived keys (time range + optional label hash) instead of relying on stable DOM IDs
**Rationale**: Focusmate DOM has no guaranteed stable identifiers. React-based SPA with hashed class names. Derived keys from observable attributes (time ranges) are more reliable than DOM attributes.

### Decision 7: Multiple DOM Selector Strategies
**Choice**: Implement multiple fallback selector strategies (accessibility labels, time text parsing, derived keys)
**Rationale**: No stable DOM identifiers exist. Multiple strategies provide resilience against DOM changes and different view contexts (day/week/upcoming views).

### Decision 8: Multiple Accounts and Calendar Groups Support
**Choice**: Support multiple Google accounts and calendar groups in options page
**Rationale**: Users may have multiple Google accounts with calendars organized in groups. UI should organize calendars by account and group for clarity.

### Decision 9: Message Passing Architecture
**Choice**: Content script requests data from background, background responds
**Rationale**: Background has access to Chrome APIs, content script has DOM access

## Alternative Approaches Considered

### Alternative 1: Content Script Direct API Calls
**Rejected**: Content scripts cannot directly use `chrome.identity` for OAuth
**Chosen**: Background service worker handles all API calls

### Alternative 2: Iframe for Overlay
**Rejected**: Iframes have cross-origin restrictions and complexity
**Chosen**: Shadow DOM provides isolation without iframe limitations

### Alternative 3: React/Vue for UI
**Rejected**: Adds complexity and bundle size for simple overlay
**Chosen**: Vanilla TypeScript with Shadow DOM is sufficient

### Alternative 4: No Caching
**Rejected**: Would hit Google Calendar API rate limits with frequent requests
**Chosen**: 60-second cache balances freshness with API limits

## Performance Considerations

### Optimization Strategies

1. **Debouncing**: MutationObserver callbacks debounced to 200ms
2. **Caching**: 60-second cache reduces API calls
3. **Lazy Loading**: Overlay only renders when enabled
4. **Efficient Selectors**: Use specific selectors, avoid deep DOM traversal
5. **Batch Operations**: Process multiple sessions/events in single pass

### Performance Targets

- Overlay render: < 500ms
- Conflict computation: < 100ms for day view
- API response time: < 2s (depends on Google Calendar API)
- Memory usage: < 50MB for extension

## Security Considerations

1. **OAuth Token Security**: Tokens managed by Chrome Identity API, not stored in extension storage
2. **API Key Storage**: Focusmate API key stored in `chrome.storage.local` (encrypted by Chrome)
3. **No Data Exfiltration**: Extension never sends calendar data to external servers
4. **Content Security Policy**: Manifest V3 CSP restrictions followed
5. **Input Validation**: All user inputs validated before storage

## Risk Assessment

### Technical Risks

1. **Focusmate DOM Changes** (High)
   - Mitigation: Multiple selector strategies (accessibility labels, time text parsing, derived keys). No reliance on stable DOM IDs. Use Google Calendar as primary source when sync enabled. Centralized selector logic with fallbacks.
   
2. **Google Calendar API Rate Limits** (Medium)
   - Mitigation: Caching, request batching
   
3. **TypeScript Build Complexity** (Low)
   - Mitigation: Use established tooling, document process
   
4. **Timezone Edge Cases** (Medium)
   - Mitigation: Use epoch milliseconds, normalize to UTC

### Mitigation Strategies

- Comprehensive error handling
- Fallback mechanisms (DOM scraping if API unavailable)
- User feedback for errors
- Debug logging for troubleshooting
